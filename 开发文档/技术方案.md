# LumeKit 技术方案

更新时间：2026-10-11

## 1. 总体方案

当前项目采用 Windows 桌面应用方案：

```text
WinUI 3 页面和窗口
        ↓
ViewModel / Navigation / DI
        ↓
应用服务和自动化服务
        ↓
Core 契约、模型和通用能力
        ↓
Infrastructure 文件、日志和系统辅助能力
        ↓
Windows API、音频设备和系统设置
```

其中 DI（依赖注入）是由应用统一创建服务，再把服务交给页面和其他服务使用，减少页面直接创建底层对象。

## 3. 项目分层

### 3.1 主项目 `BluetoothAudioReceiver`

负责页面、ViewModel、窗口、通知、托盘、自动化服务和具体业务组合。

### 3.2 Core 项目 `BluetoothAudioReceiver.Core`

负责公共模型、契约、扩展、主题/系统辅助能力和可复用服务。

### 3.3 Infrastructure 项目 `BluetoothAudioReceiver.Infrastructure`

负责文件服务、日志、启动辅助、运行时辅助和其他基础设施。

### 3.4 主项目 `Services\` 的四层职责

`BluetoothAudioReceiver\Services\` 按下面四层职责分目录。这四层的定义取自 17.0 优化方案（原 `17.0优化文档.md`，已归档到 `docs/archive/17.0优化文档.md`），是本项目归类和新增文件的判断依据。

**调度中心**

- 按需收集各模块需要的信息，不无条件收集所有系统信息。
- 统一监听、状态管理、事件分发、任务调度。

**自动化**

- 覆盖用户自定义自动化和固定场景自动化。
- 负责规则判断并调用基础能力。
- 不重复实现具体业务能力。

**基础能力**

- 提供实际系统能力，如音频、亮度、电源、主题、蓝牙、触摸板、通知等。
- 可被用户功能、自动化、后台服务共同调用。

**后台服务**

- 持续运行的自动功能，如节能、自动亮度、日夜模式、状态维护等。

核心原则：调度中心负责“收集与调度”，自动化负责“判断”，基础能力负责“执行具体能力”，后台服务负责“持续运行”。归类按现有代码职责走，尽量复用现有代码，不重复开发，不为架构而架构。

目录与文件数：

| 目录 | 文件数 | 职责 |
|---|---|---|
| `Services\Scheduling\` | 12 | 调度中心：统一监听入口、系统状态快照、事件总线、按需收集与事件发布 |
| `Services\Automation\` | 26 | 自动化：规则引擎、触发匹配、条件注册、决策、编排、执行、动作注册表和 13 个动作提供器 |
| `Services\Capabilities\` | 33 | 基础能力：音频、蓝牙、主题与外观、亮度与显示器、电源、通知与浮层、触摸板、摄像头与快捷键 |
| `Services\Background\` | 7 | 后台服务：自动亮度、自动日夜模式、后台效率、主题测试定时器、程序列表定时刷新 |

另有 9 个跨层共用的基础文件留在 `Services\` 根目录：`ActivationService.cs`、`AppJsonContext.cs`、`AppSettingsService.cs`、`BackgroundDispatchModels.cs`、`NavigationService.cs`、`NavigationViewService.cs`、`PageService.cs`、`SolarCalculator.cs`、`TaskSchedulerManager.cs`。

所有文件都使用 `namespace BluetoothAudioReceiver.Services`，目录只表达职责归属，不影响类型解析。

### 3.5 职责边界与开发判断标准

以下边界规则取自 `LumeKit架构与自动化边界.md`（已归档到 `docs/archive/LumeKit架构与自动化边界.md`）中仍然有效的部分。该文里的 `AutomationMainlineBus`、`AutomationTraceStore`、状态保存/恢复动作和 `WallpaperDimService` 都已在 17.0 优化中删除，不再作为依据。

**四条关键边界**

- 事件不等于状态：事件表示“发生了一次变化”，用于触发处理；状态表示“现在是什么情况”，用于判断条件和执行动作。
- 自动化动作不等于模块动作：自动化动作是“规则希望做什么”，模块动作是“某个模块具体怎么做”。
- 一次性动作不等于持续运行策略：一次性动作由自动化触发；持续监听并维持状态由对应功能模块自己负责，自动化不接管模块的长期策略。
- 执行不等于执行结果：发出动作不代表完成，自动化必须等待并记录最终成功或失败结果，不能只记录“已经发起”。

**模块之间的调用规则**

允许：

```text
Scheduler → Automation
Scheduler → Modules
Automation → Module Action Adapter
Module Action Adapter → 对应功能模块
功能模块 → 自己的 Controller / System API
```

不允许：

```text
Automation → 直接调用 Windows API
Audio → 直接读取 Automation Rule
Brightness → 直接修改 Power 内部状态
Module → 代替 Automation 判断规则
多个模块 → 重复监听同一个系统事件
```

**新增代码放哪**

| 新增内容的性质 | 归属 |
|---|---|
| 发现变化、采集和传递系统事实 | 调度中心（Scheduler Observation） |
| 判断某条规则是否命中、要不要执行 | 自动化（Automation） |
| 某个模块能做的事情 | 对应基础能力模块 |
| 真正调用系统完成操作 | 对应模块的 Controller 或执行部分 |
| 自动化专属的简单动作（Delay、Wait、启动/停止进程、打开链接等） | 自动化原生动作 |

最简判断方式：

```text
发生了什么？       → 调度中心
要不要执行？       → 自动化
谁有能力执行？     → 对应基础能力模块
怎么真正执行？     → 模块自己的执行部分
执行结果如何？     → 返回自动化并记录结果
```

## 5. 浮层设计基线

本节是浮层设计的唯一基线，取自原 `LumeKit 浮层设计规范.md` 和 `DeskBox与LumeKit浮层实现对比.md`（两份已归档到 `docs/archive/`），并去掉了与本文重复的部分。

参考来源：本地 `引用项目/DeskBox-main`（外部参考项目，未提交、已被忽略）、当前项目已有的通知和托盘面板实现。

### 5.1 三类浮层和统一视觉

浮层分三类，使用同一套视觉语言，但不强行做成同一种界面：

- 悬浮通知：告诉用户发生了什么。
- 托盘左键快速面板：快速查看和控制。
- 托盘右键命令菜单：执行明确命令。

托盘右键继续沿用这套结构：Windows 托盘图标 → `H.NotifyIcon` 接收右键 → WinUI `MenuFlyout` 显示菜单 → `MenuFlyoutItem` 承载文字、图标和点击动作。

所有浮层都应满足：

- 使用 WinUI 原生主题资源，背景跟随系统明暗主题。
- 文字使用 `Segoe UI Variable`；菜单可保留引用项目的中文字体兜底。
- 浮层使用 `8` 圆角；页面内的小行、小按钮使用 `4` 或 `6` 圆角。
- 不使用厚重阴影，不额外使用鲜艳的大面积品牌色。
- 重点状态优先用图标、透明度、边框和选中状态表达。
- 长文字使用省略号，不撑破浮层。

统一间距使用 `4` 的倍数：

| 用途 | 参数 |
| --- | ---: |
| 最小间距 | `4` |
| 图标和文字之间 | `8` |
| 同一行控件之间 | `8` |
| 小区块之间 | `12` |
| 浮层内容左右留白 | `16` |
| 大区块之间 | `16` 或 `24` |

统一文字层级：

| 用途 | 字号 | 字重 |
| --- | ---: | --- |
| 浮层标题 | `14` | SemiBold |
| 主要内容 | `13` 或 `14` | Regular |
| 状态值、重点信息 | `13` 或 `14` | SemiBold |
| 辅助说明 | `11` 或 `12` | Regular |
| 托盘命令菜单 | `13` | Regular |

三类浮层都要支持这些状态：默认、悬停、按下、禁用、当前选中或当前生效、深色主题、浅色主题，以及高对比度主题的基本可读性。悬停背景使用浅色的系统中性色，不单独制作一套彩色按钮。

引用项目的主要设计参数：菜单字体 `Microsoft YaHei UI, Segoe UI Variable, Segoe UI`，菜单字号 `13`，菜单最小行高 `36`，菜单项内边距 `10,8,10,8`，浮层圆角 `8`，页面内常用圆角 `4`，常用间距 `4 / 8 / 12 / 16`，轻量悬停背景约 `8%` 透明度。

### 5.2 场景一：悬浮通知

用于显示音频输入输出切换、蓝牙连接和断开、自动亮度/主题/节能状态变化、自动化执行结果、按键或状态指示器变化。通知默认只负责传达信息，只有用户确实需要马上处理时才增加操作按钮。

尺寸沿用当前项目已有的通知尺寸：

| 类型 | 宽度 | 高度 | 适用内容 |
| --- | ---: | ---: | --- |
| 标准通知 | `600` | `110` | 常规音频、设备和状态提示 |
| 紧凑通知 | `420` | `110` | 一行短提示 |
| 自动化通知 | `600` | `130` | 标题加多行执行结果 |
| 合并通知 | `600` | `180` | 主通知加短时间内追加的内容 |
| 快捷键通知 | `400` | `110` | 单个快捷键或按键状态 |

后续改通知尺寸，优先修改 `NotificationLayoutProfiles`，不要在各个调用处单独改宽高。

外观：浮层圆角 `8`；内容左右留白 `16`；普通图标区域约 `30 x 30`，图标字号约 `18`；合并通知图标区域约 `34 x 34`，图标字号约 `20`；标准正文和自动化明细 `13`；主要文字不透明，状态文字约 `68%` 不透明度；图标和正文间距 `8` 到 `12`。图标优先使用 `Segoe Fluent Icons` 或项目现有图标资源，不使用表情符号作为正式图标。

动画沿用当前项目的节奏：

| 动作 | 参数 |
| --- | ---: |
| 显示动画 | `300ms` |
| 隐藏动画 | `200ms` |
| 内容尺寸变化 | `160ms` |
| 自动隐藏 | `2500ms` |
| 入场纵向位移 | `30px` |
| 动画刷新 | `16ms` |
| 缓动力度 | `3` |

动画要求：从底部向上轻微进入，同时渐显；隐藏时向下轻微退出并渐隐；不做弹跳、旋转和大幅缩放；用户正在操作托盘面板时，可以按设置隐藏悬浮通知。

内容结构：

```text
标准通知        [图标] 主要信息                          状态值
自动化通知      [图标] 标题
                       执行结果或明细
合并通知        [图标] 主通知                          状态值
                       追加内容 1
                       追加内容 2
```

通知正文尽量控制在一到两行。超过两行时，优先使用合并通知或自动化通知布局。

### 5.3 场景二：托盘左键快速面板

左键托盘图标打开快速面板，用于查看当前音频输入输出状态、快速切换设备、查看快捷键和执行高频操作。它是“快速控制面板”，不是设置页面，也不是命令菜单。

| 参数 | 数值 |
| --- | ---: |
| 默认宽度 | `650` |
| 默认高度 | `400` |
| 最小高度 | `260` |
| 屏幕边缘安全距离 | `10` |
| 面板圆角 | `8` |

如果内容超出高度，使用纵向滚动，不把窗口无限拉长。

标题区：标题字号 `14`、SemiBold；辅助说明字号 `11`；标题区内边距 `40,10,10,10`；标题和辅助说明间距 `8`；分割线高度 `1`；分割线上方留白 `4`，下方留白 `6`。标题要直接说清楚当前面板是什么，例如“音频管理”。

设备行按 `[状态点] [设备图标] 设备名称 … 快捷键` 组织：

| 参数 | 数值 |
| --- | ---: |
| 行文字号 | `12` |
| 快捷键字号 | `12` |
| 行内边距 | `6,5,6,5` |
| 行外边距 | `4,2,4,2` |
| 行圆角 | `6` |
| 状态点半径 | `4` |
| 状态点列宽 | `20` |
| 图标列宽 | `30` |
| 名称列宽 | `170` |
| 快捷键列宽 | `220` |
| 快捷键列最小宽度 | `120` |
| 行间距 | `0` |

设备行状态：当前连接或当前使用的设备显示绿色状态点；未连接设备状态点透明，不显示灰色圆点；鼠标移入显示约 `8%` 透明度的中性色背景，移出恢复透明；点击设备立即执行连接、断开或切换；设备名称过长显示省略号；快捷键为空显示 `--`。

快捷键徽章：背景约 `8%` 透明度的中性色，圆角 `6`，内边距 `12,4,12,4`，不使用鲜艳背景色。

打开和关闭：左键托盘图标打开或关闭面板；面板显示在鼠标附近并自动避开屏幕边缘；点击面板外部关闭；再次点击托盘图标关闭；面板显示期间按设置决定是否隐藏悬浮通知；不出现在任务栏窗口切换列表中。

### 5.4 场景三：托盘右键命令菜单

右键托盘图标打开命令菜单，用于打开主界面、打开通知设置、打开音频设置、打开相关目录或工具、重启应用、退出应用。命令菜单只放“动作”，不放复杂状态展示。

推荐分组结构：

```text
打开主界面
----------------
快速切换或常用动作
打开通知设置
打开音频设置
----------------
打开相关目录
----------------
重启
退出
```

具体项目可以根据实际功能删减，但分组逻辑保持不变。

| 参数 | 数值 |
| --- | ---: |
| 菜单项最小高度 | `36` |
| 菜单项字号 | `13` |
| 菜单项内边距 | `10,8,10,8` |
| 菜单上下留白 | `4` |
| 菜单字体 | `Microsoft YaHei UI, Segoe UI Variable, Segoe UI` |
| 菜单圆角 | `8` |
| 图标和文字间距 | 采用 WinUI 默认间距 |
| 分隔线左右留白 | `8` |

菜单宽度：普通命令菜单 `176`，预留菜单外框宽度约 `192`；中文命令较长时，以最长命令完整显示为准。当前项目已有的 `92` 宽度、`30` 行高菜单仅适合作为旧版固定三行菜单，不作为新的公共标准。

每个菜单项都应有清楚的动作名称、熟悉的图标、明确的点击结果和必要时的禁用状态。推荐图标规则：打开主界面用窗口或主页图标，设置用齿轮图标，打开目录用文件夹图标，重启用刷新图标，退出用叉号图标，连接或切换用设备、箭头或音频图标。图标优先使用 WinUI 的 `SymbolIcon` 或 `Segoe Fluent Icons`，不手工画一套风格不一致的图标。

交互规则：点击菜单项后先关闭菜单，再执行动作；打开设置、主窗口等窗口动作不阻塞菜单关闭；不在菜单中放需要连续编辑的输入框，不显示大段说明文字，不把通知卡片直接嵌入命令菜单；菜单内容较多时用分隔线分组，不使用多层嵌套；菜单打开位置要靠近托盘图标，并自动避开屏幕边缘。

危险操作：“退出”“重启”放在菜单底部；“退出”可以使用普通菜单项；清除数据、恢复默认等不可逆操作不能直接放在托盘菜单里，需要确认的危险操作应打开确认对话框。

### 5.5 三类浮层的区别

| 项目 | 悬浮通知 | 托盘左键快速面板 | 托盘右键命令菜单 |
| --- | --- | --- | --- |
| 主要目的 | 告知 | 查看和控制 | 执行命令 |
| 默认尺寸 | `600 x 110` | `650 x 400` | 约 `192` 宽 |
| 圆角 | `8` | `8` | `8` |
| 内容密度 | 低 | 中 | 高 |
| 是否自动消失 | 是 | 否，点击外部关闭 | 是，点击后关闭 |
| 是否支持滚动 | 一般不支持 | 支持纵向滚动 | 尽量不需要 |
| 主要文字 | `13` | `12` | `13` |
| 标题 | 可选 | 必须有 | 不单独设置大标题 |
| 操作数量 | 少量 | 多个快速操作 | 多个命令 |
| 适合放状态 | 是 | 是 | 少量，不作为主体 |

### 5.6 参数入口与修改顺序

已有的参数入口继续保留：

- 通知尺寸：`Contracts/Services/NotificationLayoutProfiles.cs`

需要调整浮层时按这个顺序：先改公共浮层参数，再改具体场景的尺寸参数，最后才处理某个特殊内容的局部例外。不要在多个窗口里分别写相同的圆角、字号和间距。

## 6. 技术来源

### 官方接口

- WinUI 3、Windows App SDK、Windows SDK。
- Windows 原生 API 和系统设置能力。
- CsWin32 生成 Windows API 调用代码。
- WMI 和 Windows Task Scheduler。

### 成熟方案

- CommunityToolkit.Mvvm：MVVM（界面和业务状态分离）支持。
- Microsoft.Extensions.Hosting：服务注册和生命周期。
- H.NotifyIcon：系统托盘。
- WinUIEx：窗口辅助。
- Serilog：日志。
- AudioPlaybackConnector：音频播放设备连接能力。

### 自研代码

- LumeKit 的页面、业务服务、自动化规则、动作提供器、通知业务和浮层整合。
- DeskBox 浮层适配、浮层配置档和当前 LumeKit 的窗口生命周期。

## 7. 选择原因

- 项目目标是 Windows 桌面工具，WinUI 3 和 Windows App SDK 与目标平台匹配。
- 系统音频、亮度、电源和窗口能力需要调用 Windows 原生接口。
- 已有成熟库可以处理 MVVM、托盘、日志和窗口辅助，减少重复开发。
- 业务代码按功能服务拆分，便于自动化调用和后续替换实现。

## 8. 当前限制和风险

1. 主项目和 Core 项目已统一到 Windows App SDK 2.4.0 与 WinUIEx 2.9.3，原先的版本偏差已消除。
2. 自动化总架构文档覆盖面大于当前代码已验证范围，不能把设计图当作完成清单。
3. 第 5 节的浮层仍是独立新实现，只服务测试入口；旧通知、托盘面板和右键菜单尚未全部切换。
4. 部分功能依赖具体硬件、驱动、Windows 版本或管理员权限。
5. 本机处于离线环境：命令行构建需要把仓库内的 `.dotnet-home` 当作 NuGet 缓存和 CLI 主目录，并且必须加 `-m:1 -nodeReuse:false` 才会正常执行；新增第三方包或测试框架目前无法还原。
6. 仓库内没有任何自动测试，回归只能人工执行；真实设备验收一项未做。
7. 主项目声明了 `IsAotCompatible`，但仍有 93 个 XAML 绑定告警和 1 个第三方库过时告警未处理。
8. 第 5.7 节列出的两处浮层参数冲突尚未确认，落地前必须先定口径。

## 9. 判断方案是否合适

当前方案对“Windows 音频管理工具”是匹配的，主要功能也沿用了官方接口和成熟库。现在最需要优先确认的不是换技术栈，而是：

- [已完成] 统一 Windows App SDK 版本并重新构建：版本已统一到 2.4.0 与 2.9.3，命令行 Debug x64 构建 0 个错误。
- 用验收标准逐项验证真实设备、托盘、通知和自动化。
- 明确哪些自动化观察源已经实现，哪些仍属于规划。
- 在普通通知稳定后，再决定是否推广 DeskBox 浮层。
