# LumeKit 技术方案

更新时间：2026-10-05

## 1. 总体方案

当前项目采用 Windows 桌面应用方案：

```text
WinUI 3 页面和窗口
        ↓
ViewModel / Navigation / DI
        ↓
应用服务和自动化服务
        ↓
Core 契约、模型和通用能力
        ↓
Infrastructure 文件、日志和系统辅助能力
        ↓
Windows API、音频设备和系统设置
```

其中 DI（依赖注入）是由应用统一创建服务，再把服务交给页面和其他服务使用，减少页面直接创建底层对象。

## 2. 技术栈

| 领域 | 当前代码采用 | 说明 |
|---|---|---|
| 开发语言 | C# | 主要代码语言 |
| UI | WinUI 3 + XAML | Windows 原生现代界面 |
| 运行时 | .NET 10 Windows | 三个项目均目标为 `net10.0-windows10.0.22621.0` |
| Windows 框架 | Windows App SDK | 主项目和 Core 项目统一为 2.4.0；窗口辅助库 WinUIEx 统一为 2.9.3 |
| 页面状态 | CommunityToolkit.Mvvm | ViewModel 和绑定辅助 |
| 服务创建 | Microsoft.Extensions.Hosting / DI | 在 `App.xaml.cs` 统一注册 |
| Windows 调用 | CsWin32、Windows SDK、WMI、系统组件 | 访问原生 Windows 能力 |
| 音频 | AudioPlaybackConnector 相关方案及 Windows 音频接口 | 音频连接和路由 |
| 托盘 | H.NotifyIcon.WinUI | 系统托盘图标和入口 |
| 窗口辅助 | WinUIEx | 窗口和 WinUI 辅助能力 |
| 文件和配置 | JSON、LocalSettings、文件服务 | 设置和自动化规则持久化 |
| 日志 | Serilog | Infrastructure 层日志 |
| 后台任务 | TaskScheduler | 系统任务调度相关功能 |

## 3. 项目分层

### 3.1 主项目 `BluetoothAudioReceiver`

负责页面、ViewModel、窗口、通知、托盘、自动化服务和具体业务组合。

### 3.2 Core 项目 `BluetoothAudioReceiver.Core`

负责公共模型、契约、扩展、主题/系统辅助能力和可复用服务。

### 3.3 Infrastructure 项目 `BluetoothAudioReceiver.Infrastructure`

负责文件服务、日志、启动辅助、运行时辅助和其他基础设施。

## 5. 技术来源

### 官方接口

- WinUI 3、Windows App SDK、Windows SDK。
- Windows 原生 API 和系统设置能力。
- CsWin32 生成 Windows API 调用代码。
- WMI 和 Windows Task Scheduler。

### 成熟方案

- CommunityToolkit.Mvvm：MVVM（界面和业务状态分离）支持。
- Microsoft.Extensions.Hosting：服务注册和生命周期。
- H.NotifyIcon：系统托盘。
- WinUIEx：窗口辅助。
- Serilog：日志。
- AudioPlaybackConnector：音频播放设备连接能力。

### 自研代码

- LumeKit 的页面、业务服务、自动化规则、动作提供器、通知业务和浮层整合。
- DeskBox 浮层适配、浮层档案和当前 LumeKit 的窗口生命周期。

## 6. 选择原因

- 项目目标是 Windows 桌面工具，WinUI 3 和 Windows App SDK 与目标平台匹配。
- 系统音频、亮度、电源和窗口能力需要调用 Windows 原生接口。
- 已有成熟库可以处理 MVVM、托盘、日志和窗口辅助，减少重复开发。
- 业务代码按功能服务拆分，便于自动化调用和后续替换实现。

## 7. 当前限制和风险

1. 主项目和 Core 项目已统一到 Windows App SDK 2.4.0 与 WinUIEx 2.9.3，原先的版本偏差已消除。
2. 自动化总架构文档覆盖面大于当前代码已验证范围，不能把设计图当作完成清单。
3. DeskBox 浮层目前是独立的新实现，旧通知、托盘面板和右键菜单尚未全部切换。
4. 部分功能依赖具体硬件、驱动、Windows 版本或管理员权限。
5. 本机处于离线环境：命令行构建需要把仓库内的 `.dotnet-home` 当作 NuGet 缓存和 CLI 主目录，并且必须加 `-m:1 -nodeReuse:false` 才会正常执行；新增第三方包或测试框架目前无法还原。
6. 仓库内没有任何自动测试，回归只能人工执行；真实设备验收一项未做。
7. 主项目声明了 `IsAotCompatible`，但仍有 93 个 XAML 绑定告警和 1 个第三方库过时告警未处理。

## 8. 判断方案是否合适

当前方案对“Windows 音频管理工具”是匹配的，主要功能也沿用了官方接口和成熟库。现在最需要优先确认的不是换技术栈，而是：

- [已完成] 统一 Windows App SDK 版本并重新构建：版本已统一到 2.4.0 与 2.9.3，命令行 Debug x64 构建 0 个错误。
- 用验收标准逐项验证真实设备、托盘、通知和自动化。
- 明确哪些自动化观察源已经实现，哪些仍属于规划。
- 在普通通知稳定后，再决定是否推广 DeskBox 浮层。
